- **ผู้เผยแพร่**: สำนักงานนโยบายและแผนการขนส่งและจราจร (สนข.) กระทรวงคมนาคม
- **เวอร์ชันที่มีอยู่ในมือ**: `feed_version = 20260919`, `Last-Modified: Sat, 19 Sep 2026 18:02:09 GMT`, 41,844,577 ไบต์

## Bottom line

- **สัญญาอนุญาตยืนอยู่บนพื้นแข็ง** — CC-BY 4.0 ไม่ได้มาจาก Transitland อย่างที่ตั้งข้อสงสัยไว้ในตั๋ว แต่ประกาศโดย สนข. เองที่ <https://namtang-api.otp.go.th/opendata> ซึ่งเป็นหน้าเดียวกับที่วางลิงก์ดาวน์โหลดไฟล์นี้ไว้ → ประโยคอนุญาตกับไฟล์ที่เราถืออยู่เป็นของคู่กันโดยตรง ใช้ต่อ ดัดแปลง และเก็บสำเนาได้ ขอแค่ให้เครดิต
- **แต่ประกาศนั้นบาง** — ไม่มีไฟล์ `LICENSE` ในซิป ไม่มีฟิลด์สัญญาอนุญาตใน `feed_info.txt` ไม่มีเอกสาร Terms of Use แยกต่างหาก และตัวหนังสือเขียนแค่ "Creative Commons CC-BY" เลข **4.0 อยู่ในลิงก์ปลายทางเท่านั้น** ไม่ได้เขียนเป็นตัวอักษร
- **ฟีดถูก build ใหม่ทุกวัน** — Transitland เก็บได้ 100 เวอร์ชันติดกันทุกวันตั้งแต่ 2026-06-11 ถึง 2026-09-19 โดย SHA1 ไม่ซ้ำกันสักวัน และขนาดไฟล์โต 38.8 MB → 41.8 MB ในห้าสัปดาห์ นี่ไม่ใช่ฟีดนิ่ง
- **URL ทับไฟล์เดิมตลอด ไม่มี URL แบบระบุเวอร์ชัน ไม่มี changelog** — สนข. ไม่เก็บประวัติเลย คนที่เก็บคือบุคคลที่สาม ถ้าเราอยากได้ประวัติ เราต้องเก็บเอง
- **`Last-Modified` พอใช้เช็ค แต่ conditional GET ใช้ไม่ได้** — เซิร์ฟเวอร์ไม่คืน 304 และไม่มี `ETag` วิธีที่ใช้ได้จริงคือยิง HEAD แล้วเทียบคู่ (`Last-Modified`, `Content-Length`) กับที่เก็บไว้
- **ช่องทางติดต่อเดียวที่ฟีดประกาศเองคือ Facebook Messenger** ไม่มีอีเมล ไม่มีเอกสารนักพัฒนา และ `feed_publisher_url` ในไฟล์ **พิมพ์ผิดจน DNS ไม่ resolve** — เป็นสัญญาณว่า metadata ไม่ได้ถูกดูแลอย่างใกล้ชิด

### สิ่งที่ *ไม่* พบ (และควรรู้ว่าไม่พบ)

- **ไม่มีไฟล์ `LICENSE`, `COPYING`, หรือ `README` ในซิป** — ในซิปมี 13 ไฟล์ ล้วนเป็น `.txt` ของ GTFS เท่านั้น
- **`feed_info.txt` ไม่มีฟิลด์สัญญาอนุญาต** — GTFS spec ไม่มีฟิลด์นี้อยู่แล้ว แต่ก็แปลว่าไฟล์ไม่พกหลักฐานสัญญาอนุญาตติดตัวมา ถ้าไฟล์หลุดออกจากบริบทของหน้าเว็บ ก็ไม่เหลืออะไรให้อ้าง
- **ไม่มีเอกสาร Terms of Use / เงื่อนไขการใช้ข้อมูล แยกเป็นหน้าต่างหาก** ไม่มีวันที่ประกาศ ไม่มีเลขที่หนังสือ ไม่มีอะไรที่ดูเป็นเอกสารทางการ — หน้า `/opendata` เป็นหน้า HTML เปล่าๆ ไม่มี CSS framework ยาวประมาณย่อหน้าเดียว
- **เลขเวอร์ชัน "4.0" ไม่ได้ถูกเขียนเป็นตัวอักษร** อยู่ใน `href` ของลิงก์เท่านั้น ในทางปฏิบัติถือว่าชัดพอ (CC แนะนำให้ระบุเวอร์ชันเสมอ และลิงก์ก็ชี้ 4.0) แต่ถ้าวันหนึ่งมีข้อโต้แย้ง จุดนี้คือจุดที่บาง
- **ไม่มีประโยคใดพูดถึงการใช้เชิงพาณิชย์หรือการเผยแพร่ซ้ำโดยเฉพาะ** — ต้องอาศัยตัวสัญญา CC-BY 4.0 เอง ซึ่งอนุญาตทั้งสองอย่างอยู่แล้ว
- **`otp.gdcatalog.go.th` (บัญชีข้อมูลของ สนข.) ไม่ได้ลงทะเบียนฟีด GTFS นี้ไว้** — ที่ติดแท็ก `Namtang` มีแค่สองชุดที่เป็น *สถิติการใช้งานแอป* (`dataset_12_04`, `dataset_12_05`, ระบุ licence เป็น "Open Data Common", ปรับปรุง 21 พ.ค. 2569) ไม่ใช่ตัวข้อมูลการเดินรถ → **อย่าไปอ้าง licence จากแคตตาล็อกนั้นโดยเข้าใจผิดว่าเป็นของฟีดเดียวกัน มันคนละชุด และระบุสัญญาคนละแบบ**

## 3. จะรู้ได้ยังไงว่ามีเวอร์ชันใหม่

### สิ่งที่เซิร์ฟเวอร์ให้ (ผลจริงจากการยิง HEAD)

```
HTTP/1.1 200 OK
Server: nginx/1.24.0 (Ubuntu)
Content-Type: application/zip
Content-Length: 41844577
Cache-Control: public
Last-Modified: Sat, 19 Sep 2026 18:02:09 GMT
Content-Disposition: attachment; filename=namtang-gtfs.zip
Accept-Ranges: bytes
```

| กลไก | มีไหม | สรุป |
|---|---|---|
| `Last-Modified` | ✅ มี | เชื่อถือได้ ตรงกับ `feed_version` |
| `Content-Length` | ✅ มี | ใช้เป็นสัญญาณเสริมได้ดี |
| `ETag` | ❌ **ไม่มี** | nginx ปิดไว้ |
| Conditional GET (`If-Modified-Since` → 304) | ❌ **ใช้ไม่ได้** | ทดสอบแล้วทั้ง HEAD และ GET คืน 200/206 ไม่เคยคืน 304 |
| `Accept-Ranges: bytes` | ✅ มี | ยิง `Range: bytes=0-99` แล้วได้ 206 + 100 ไบต์ จริง |
| `Cache-Control` | `public` ไม่มี `max-age` | ตัวกลางอาจ cache ตามใจ — ถ้าเจออาการค้าง ให้เติม cache-buster |

### วิธีที่แนะนำ

**ยิง HEAD แล้วเทียบคู่ `(Last-Modified, Content-Length)` กับค่าที่เก็บไว้** ถ้าค่าใดค่าหนึ่งต่าง → ดึงไฟล์เต็ม แล้วอ่าน `feed_version` จาก `feed_info.txt` เพื่อยืนยัน

- ต้นทุนต่อการเช็ค: ~200 ไบต์ ตอบกลับภายในไม่ถึงวินาที
- ความถี่ที่เหมาะสม: **วันละครั้ง ช่วงเช้าตามเวลาไทย** (ไฟล์เสร็จราวตี 1–2) ถี่กว่านี้ไม่ได้ประโยชน์
- **`ETag` ใช้ไม่ได้ และ conditional GET ก็ใช้ไม่ได้** — ตอบคำถามในตั๋วตรงๆ ว่า `Last-Modified` "พอ" แต่ต้องใช้แบบ poll-and-compare เองเท่านั้น ไม่มีทางลัดให้เซิร์ฟเวอร์บอกว่า "ไม่เปลี่ยน"

### ข้อควรระวังที่สำคัญกว่ากลไก

**`Last-Modified` เปลี่ยนทุกวัน ไม่ว่าข้อมูลจริงจะเปลี่ยนหรือไม่** มันบอกว่า "ถูก build ใหม่" ไม่ได้บอกว่า "ข้อมูลที่เราสนใจเปลี่ยน" ถ้าเอามาจุดชนวน pipeline ตรงๆ แอปจะ re-import ทุกวันโดยเปล่าประโยชน์ 41 MB

ทางที่ควรทำคือให้ HEAD เป็นแค่ *ประตูบานแรก* แล้วตัดสินจริงด้วยการ hash เฉพาะไฟล์ที่แอปใช้ (`routes.txt`, `stops.txt`, `trips.txt`, `stop_times.txt`, `shapes.txt`) หลังแตกซิป — `fare_attributes.txt` + `fare_rules.txt` รวมกัน 65 MB จาก 224 MB ที่แตกออกมา และแอปน่าจะไม่ใช้เลย การตัดสองไฟล์นี้ออกจากการเทียบจะลด false positive ไปได้มาก

*(มีลูกเล่นที่เป็นไปได้: `Accept-Ranges` เปิดอยู่ จึงดึงเฉพาะ central directory ท้ายซิปแล้วอ่าน CRC32 ของสมาชิกแต่ละไฟล์ได้โดยไม่ต้องโหลด 41 MB — ทำให้รู้ว่าไฟล์ไหนเปลี่ยนด้วยต้นทุนไม่กี่ KB แต่เป็นงานประณีต เก็บไว้เป็นทางเลือกถ้าแบนด์วิดท์กลายเป็นปัญหา)*

## Confidence and gaps

### มั่นใจสูง (ยืนยันจากแหล่งปฐมภูมิหรือทดสอบเอง)

- **สัญญาอนุญาตคือ CC-BY (ลิงก์ชี้ 4.0) ประกาศโดย สนข. บนโดเมนราชการ ในหน้าเดียวกับลิงก์ดาวน์โหลดไฟล์นี้** — อ่านจาก HTML ต้นฉบับโดยตรง ไม่ผ่านตัวสรุป
- ทะเบียนทั้ง Transitland และ Mobility Database บันทึกตรงกัน และ MDB ทำเครื่องหมาย `is_official = True`
- ไม่มีไฟล์ LICENSE ในซิป — นับไฟล์เองแล้ว
- ฟีด build ใหม่ทุกวัน 100 วันติดโดย SHA1 ไม่ซ้ำ
- ไม่มี URL แบบระบุเวอร์ชัน ไม่มี directory listing ไม่มี changelog — ยิงทดสอบทุกรูปแบบแล้ว
- `Last-Modified` มี, `ETag` ไม่มี, conditional GET ไม่คืน 304, range request ใช้ได้ — ยิงทดสอบเองทั้งหมด
- ไม่มีเอกสารนักพัฒนา — ยิงทดสอบ path มาตรฐานและค้นเว็บสองภาษาแล้ว
- `feed_publisher_url` พิมพ์ผิดจน DNS ไม่ resolve
- สถานะของ mirror ทั้งสาม — ยิง HEAD และ CDX เองทั้งหมด

### มั่นใจปานกลาง

- **"ประวัติย้อนหลังได้ถึง 2026-06-11"** — นั่นคือเท่าที่หน้าเว็บสาธารณะของ Transitland แสดง อาจเป็นเพราะการแบ่งหน้าหรือ retention policy ไม่ใช่วันเริ่มจริง ไม่ได้ไล่หน้าต่อ
- **"build ตี 1–2 ตามเวลาไทย"** — อนุมานจาก `Last-Modified` ของสามไฟล์ในวันเดียว ยังไม่ได้เฝ้าดูหลายวันเพื่อยืนยันว่าเวลาคงที่

### ยืนยันไม่ได้ (และนี่คือส่วนที่โปรเจกต์ควรรู้ว่ายังไม่มั่นคง)

1. **ไม่มีเอกสารสัญญาอนุญาตที่เป็นทางการกว่าย่อหน้าเดียวบนหน้า HTML** ไม่มีวันที่ประกาศ ไม่มีเลขหนังสือ ไม่มีลายเซ็น ไม่มีหน้า Terms of Use — ถ้าวันหนึ่งหน้านั้นถูกแก้หรือหายไป **หลักฐานเดียวที่เรามีคือสำเนาที่เราเก็บไว้เอง** → ควร archive หน้า `/opendata` ไว้เป็นไฟล์ (หรือสั่ง Wayback ให้ snapshot) พร้อมวันที่ ก่อนจะเขียนโค้ดทับลงไป
2. **เลข "4.0" ไม่ได้เขียนเป็นตัวอักษร** อยู่ใน href เท่านั้น
3. **สนข. ไม่เคยประกาศความถี่การอัปเดตด้วยตัวเอง** — "ทุกวัน" เป็นข้อสรุปจากหลักฐานภายนอก ไม่ใช่คำมั่นของผู้เผยแพร่ วันหนึ่งอาจเปลี่ยนเป็นรายสัปดาห์โดยไม่บอกใครก็ได้
4. **ไม่รู้ว่าช่องทาง Facebook ตอบจริงไหม** ไม่ได้ทัก (จะเป็นการส่งข้อความในนามผู้ใช้) ถ้าอยากทดสอบต้องให้เจ้าของโปรเจกต์ทักเอง
5. **ไม่รู้ว่า `stop_id` / `route_id` นิ่งข้ามเวอร์ชันหรือไม่** — มีฟีดอยู่เวอร์ชันเดียวจึง diff ไม่ได้ **นี่คือช่องว่างที่ใหญ่ที่สุดที่เหลืออยู่** และเป็นสิ่งที่ MAP ต้องการคำตอบในหัวข้อ "การอัปเดตฟีดในระยะยาว" — ควรตั้งเป็น ticket แยก โดยเริ่มจากเก็บสำเนาสองเวอร์ชันห่างกันสัก 1–2 สัปดาห์แล้วเทียบ (หรือดึงเวอร์ชันเก่าจาก Transitland / IA snapshot 2026-08-13 มา diff กับที่มีอยู่ ซึ่งจะได้คำตอบทันทีโดยไม่ต้องรอ)
6. **ไม่รู้ว่าเนื้อข้อมูลเปลี่ยนจริงทุกวัน หรือ SHA1 ต่างเพราะ zip ใหม่** — แยกไม่ได้จากภายนอก แต่ขนาดที่โต 3 MB ในห้าสัปดาห์บอกว่าอย่างน้อยก็เปลี่ยนจริงในระดับสัปดาห์
7. **ไม่ได้ดึงอีเมลนักพัฒนาจากหน้า Google Play / App Store** (หน้าเป็น JS-heavy ดึงไม่ติด) — เป็นช่องทางติดต่อที่ยังมีโอกาสหาเจอ ถ้าต้องการช่องที่ไม่ใช่ Facebook

### ข้อสรุปต่อคำถามตั้งต้นของตั๋ว

> "ทั้งโปรเจกต์ตั้งอยู่บนฟีดเดียว ก่อนจะสร้างอะไรทับลงไปต้องรู้ว่ามันยืนอยู่บนอะไร"

**เรื่องสัญญาอนุญาต: ยืนอยู่บนพื้นแข็ง** ใช้ได้ ดัดแปลงได้ เก็บสำเนาได้ เผยแพร่ซ้ำได้ ให้เครดิตแล้วจบ ความเสี่ยงทางกฎหมายต่ำมาก โดยเฉพาะเมื่อแอปนี้ใช้คนเดียวไม่ขึ้น store

**เรื่องความต่อเนื่องของฟีด: ยืนอยู่บนขาเดียว** URL เดียว ไม่มีข้อตกลง ไม่มี changelog ไม่มี mirror ที่สด ติดต่อได้ทาง Facebook อย่างเดียว ความเสี่ยงนี้แก้ไม่ได้ด้วยการเจรจา แต่แก้ได้ด้วยการเก็บสำเนาเอง — ซึ่งสัญญาอนุญาตอนุญาตเต็มที่ **สองข้อนี้ประกอบกันแล้วลงตัวพอดี: สิ่งที่เปราะที่สุด (ต้นทาง) แก้ได้ด้วยสิ่งที่แข็งที่สุด (สิทธิในการทำสำเนา)**
