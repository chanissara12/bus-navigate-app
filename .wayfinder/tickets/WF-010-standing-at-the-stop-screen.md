## Question

คำว่า "ดูง่าย" ในโจทย์ตั้งต้น ต้องแปลงเป็นของที่กดได้จริงแล้วเอามาเถียงกัน สร้างต้นแบบหยาบๆ ด้วยข้อมูลสายจริงในกรุงเทพสัก 2 ถึง 3 สาย

สิ่งที่ต้นแบบต้องทำให้ตัดสินใจได้:

1. **ลำดับความสำคัญบนจอ** — ช่องค้นเลขสาย กับรายการสายที่ไปจุดหมายที่บันทึกไว้ อะไรอยู่บนสุด ตอนหยิบมือถือขึ้นมาที่ป้าย อยากเห็นอะไรก่อน
2. **เลขสายต้องใหญ่แค่ไหน** — ต้องอ่านจากมือถือได้ในจังหวะเดียวกับที่เงยหน้ามองเลขข้างรถ
3. **บอกทิศยังไงให้ตาเห็นจริง** — ขึ้นกับผลของ WF-003 ถ้าแยกฝั่งได้ก็บอกฝั่งได้ ถ้าไม่ได้ต้องหันไปบอกด้วยชื่อปลายทางหน้ารถแทน
4. **แสดงลำดับป้ายทั้งสายยังไง** — สายหนึ่งมีหลายสิบป้าย จะให้เห็นทั้งสายในจอเดียว หรือเห็นแค่ช่วงรอบตัว และป้ายไร้ชื่อแทรกอยู่ด้วยตามที่เคาะใน WF-007
5. **หน้าตาตอนแอปไม่แน่ใจ** — ไม่มีสายตรง ไม่รู้ชื่อป้าย GPS เพี้ยน สามสถานะนี้ต้องดูออกทันทีว่าอย่าเพิ่งเชื่อ

ต้นแบบนี้ใช้แล้วทิ้ง ไม่ใช่โค้ดชุดแรกของแอปจริง

## ต้นแบบ (ใช้แล้วทิ้ง)

`prototypes/wf-010-standing-at-the-stop/index.html` — ไฟล์เดียวจบ ดับเบิลคลิกเปิดได้ ข้อมูลฝังอยู่ในไฟล์
สลับ variant ด้วยปุ่มลูกศรที่แถบล่าง หรือคีย์บอร์ด ← → (`?variant=A|B|C` ใช้ได้เมื่อเปิดจากไฟล์ตรงๆ)

**ฉากที่ใช้**: ยืนที่ **อนุสาวรีย์ชัยสมรภูมิ (เกาะพญาไท)** จะไป **สยามสแควร์** — ข้อมูลจริงจากฟีด Namtang 20260919
ป้ายนี้มี **37 สาย/ทิศ** ของ ขสมก. + TSB จอด และมีแค่ **8 สาย** ที่ไปถึงสยาม (นับป้ายปลายทางในรัศมีเดิน 450 ม.)
ตัวสร้างข้อมูลอยู่ใน scratchpad (`build_data.js`) ผลลัพธ์ที่ใช้จริงคือ `data.json` ข้างไฟล์ต้นแบบ

**สาม variant**

- **A — รายการที่ถือรอ**: รายการเลขสายตัวใหญ่ที่ขึ้นได้ 8 สาย พร้อมข้อความหน้ารถและจำนวนป้ายที่เหลือ อีก 29 สายพับเก็บไว้กดดูได้ว่ามันไปไหน — ถือจอไว้ในมือแล้วเทียบกับรถที่เข้าป้าย
- **B — แป้นกดเลขสาย**: กดเลขที่เห็นข้างรถ แล้วเต็มจอตอบ ขึ้นได้/อย่าขึ้น รับทั้งเลขใหม่และเลขเก่า ใช้ได้ทั้งตอนยืนรอและตอนนั่งอยู่บนรถที่ขึ้นผิด
- **C — แถบเส้นทาง**: ชิปเลขสายด้านบน เลือกแล้วเห็นลำดับป้ายทั้งสายเป็นแนวตั้ง มีหมุด "คุณอยู่ตรงนี้" กับ "ลงตรงนี้" — ตอบคำถาม "คันนี้จะพาฉันไปไหน" ตรงที่สุด

**หมายเหตุ**: โปรเจกต์นี้ยังไม่ใช่ git repo จึงยังเก็บต้นแบบขึ้น branch ใช้แล้วทิ้งตามที่ skill กำหนดไม่ได้ ต้องย้ายออกจาก main เมื่อ init git แล้ว

**ยังรอคำตอบ**: variant ไหนชนะ หรือจะเอาส่วนไหนของแต่ละตัวมาผสมกัน

## รอบที่ 2 — variant D ตามที่ขอ

**D — รายการ + ช่องกดเลข** (ตั้งเป็นค่าเริ่มต้นแล้ว): เอาโครงของ A มาเป็นฐาน แล้ววางช่องกรอกของ B ไว้ด้านบนแบบ sticky
ไม่มีแป้นกดในแอป ใช้ `inputmode="numeric"` เรียกแป้นตัวเลขของเครื่องขึ้นมาแทน

- ว่างไว้ → เห็นรายการ 8 สายที่ขึ้นได้ตามปกติ พับ 18 สายที่เหลือไว้
- พิมพ์ → การ์ดตัดสิน **ขึ้นได้/อย่าขึ้น/ไม่รู้จัก** โผล่ใต้ช่อง และรายการข้างล่างกรองตามเลขที่พิมพ์
- จับคู่โดยตัดอักขระที่ไม่ใช่ตัวเลขและตัวอักษรทิ้ง → พิมพ์ `244` เจอ `2-44` และพิมพ์ `54` ก็เจอ ไม่ต้องหาปุ่มขีด

**บั๊กที่แก้ระหว่างทาง**: รอบแรกสร้าง DOM ใหม่ทั้งหน้าทุกครั้งที่พิมพ์แล้วโฟกัสกลับเข้าช่อง ซึ่งพังแน่บนมือถือจริง (ลบตัวเลขไม่ได้ และ IME ภาษาไทยจะเพี้ยน) แก้เป็นอัปเดตเฉพาะการ์ดกับรายการ ไม่แตะช่องกรอกเลย

## สิ่งที่ต้นแบบเผยออกมา — ข้อมูลต้องกรองก่อนใช้

ต้นแบบทำให้เห็นสองอย่างที่มองไม่ออกจากสเปค และเป็นข้อจำกัดที่ของจริงต้องรับมือ

1. **รถที่สุดสายที่ป้ายนี้ — 9 จาก 37 รายการ** มี `totalAhead = 0` คือป้ายนี้เป็นป้ายสุดท้ายของมัน ขึ้นไปก็ไม่ไปไหน ถ้าไม่กรองออก แอปจะโชว์ `3-8 (38)` คู่กับปลายทาง "อนุสาวรีย์ชัยสมรภูมิ" ซึ่งคือป้ายที่ผู้ใช้ยืนอยู่ **การแสดงรถที่จอดป้ายนี้ ไม่เท่ากับการแสดงรถที่ขึ้นได้จากป้ายนี้**
2. **ระเบียนซ้ำในฟีด** — `1-8 (59)` และ `3-42 (62)` แต่ละสายมี `route_id` สองตัวที่เนื้อหาเหมือนกันทุกอย่าง (`486`/`2636` และ `2464`/`2516`) ทำให้รายการมีบรรทัดซ้ำ ต้องรวมด้วยคู่ (เลขสาย, ปลายทางหน้ารถ, จำนวนป้าย) — สอดคล้องกับที่ WF-011 เจอว่าฟีดรอบล่าสุดลบระเบียนซ้ำทิ้ง 11 สาย แปลว่ายังมีเหลืออยู่

หลังกรองสองข้อนี้: ป้ายนี้เหลือ **26 สาย/ทิศที่ขึ้นได้จริง** และ **8 สายที่ไปถึงสยาม**

## รอบที่ 3 — แผนที่เส้นทาง

กดแถวไหนก็ได้ในรายการ (ทั้งสายที่ขึ้นได้และไม่ได้) เปิดแผ่นซ้อนขึ้นมา มีสองส่วนต่อกัน

1. **แผนที่** — เส้นทางจริงจาก `shapes.txt` ของฟีด วาดเฉพาะช่วงที่วิ่งต่อจากป้ายที่ยืนอยู่ไป เส้นเขียวถ้าไปถึงจุดหมาย เส้นแดงถ้าไม่ถึง พร้อมหมุดป้ายที่ยืน หมุดป้ายที่ต้องลง จุดป้ายระหว่างทาง และวงประแสดงรัศมีเดิน 450 ม. รอบจุดหมาย
2. **ลำดับป้าย** — แถบแนวตั้งแบบเดียวกับ variant C ต่อท้ายแผนที่

**ตัดสินใจไปแล้วระหว่างทาง: ไม่ใช้แผนที่ออนไลน์** วาดเป็น SVG จากพิกัดในฟีดเอง เพราะ

- ต้องเปิดได้ตอนเน็ตห่วยที่ป้าย ซึ่งเป็นสถานการณ์ที่แอปนี้มีอยู่เพื่อรองรับ
- ไม่ต้องพึ่ง CDN หรือ tile server ที่มีโควตาและ ToS เรื่องการแคช
- ราคาที่จ่ายคือ **ไม่มีถนนหรือแม่น้ำเป็นฉากหลัง** เห็นแค่รูปทรงของเส้นทางลอยๆ ซึ่งยังไม่รู้ว่าพอสำหรับคนที่ยืนอยู่จริงหรือไม่ — **ข้อนี้ต้องให้คนตัดสิน**

ข้อมูลต้นแบบโตจาก 106 KB เป็น 165 KB เพราะเพิ่มเส้นทาง (ลดจุดเหลือสายละไม่เกิน 140 จุด) ซึ่งเป็นตัวเลขจริงที่ส่งต่อให้ WF-009 ได้ว่าเส้นทางกินที่เท่าไหร่ต่อสาย

## รอบที่ 4 — ฉากหลัง

"ดูไม่ออก" คือคำตอบที่ตรงที่สุดของรอบก่อน จึงเพิ่มฉากหลังให้ **โดยไม่ใช้แผนที่ออนไลน์** เพราะถ้าทดสอบด้วย tile แล้วดูรู้เรื่อง เราจะไม่ได้เรียนรู้เลยว่าเวอร์ชันที่ใช้ออฟไลน์ได้จริงจะดูรู้เรื่องไหม

ดึงจาก OpenStreetMap ผ่าน Overpass (ต้องใช้มิเรอร์ `overpass.private.coffee` เพราะ `overpass-api.de` และ `kumi.systems` ตอบ timeout) ในกรอบ 48.6 × 35.3 กม. ที่ครอบคลุมทั้ง 26 สาย เอา `waterway=river` กับ `highway` ระดับ motorway/trunk/primary

ลดจุดด้วย Douglas-Peucker ที่ความคลาดเคลื่อน 30 ม. (แม่น้ำ 40 ม.) และตัดเส้นสั้นกว่า 250 ม. ทิ้ง

| | เส้น | จุด |
| --- | ---: | ---: |
| แม่น้ำ/คลอง | 451 | 2,348 |
| ถนนสายหลัก | 2,119 | 4,717 |

**รวม 135 KB** จาก 6,544 ways ที่ดึงมาดิบๆ (เหลือ 2,570) — ตัวเลขนี้ส่งต่อให้ WF-009 ได้ว่าฉากหลังกินที่เท่าไหร่ต่อพื้นที่เท่านี้

ตอนวาดจะตัดเฉพาะเส้นที่อยู่ในกรอบของสายนั้น บวกขอบ 12% และวางไว้ใต้เส้นทางรถ พร้อมป้ายกำกับ "ป้ายที่ยืน" กับชื่อจุดหมาย

**ข้อจำกัดที่ยังอยู่**: มีแค่ถนนสายหลัก ไม่มีซอย ไม่มีชื่อถนน — ถ้ายังดูไม่ออกอยู่ ทางที่เหลือคือใส่ชื่อถนน หรือยอมใช้แผนที่ออนไลน์แล้วรับผลเรื่องออฟไลน์

**โผล่ประเด็นใหม่**: ข้อมูล OSM เป็น **ODbL** ซึ่งเป็นคนละสัญญาอนุญาตกับฟีด Namtang ที่เป็น CC-BY การเอามาอบรวมกันในไฟล์เดียวมีเงื่อนไขเรื่องการให้เครดิตและ share-alike ที่ต้องดูให้ชัด แตกเป็น [WF-012](WF-012-osm-odbl-licence.md)

## รอบที่ 5 — ชื่อถนน และตัวเลข performance ที่วัดจริง

**ชื่อถนน**: ดึงจาก dump ของ Overpass ที่มีอยู่แล้ว ไม่ต้องยิงใหม่ เดินไปตามเส้นแล้วหยอดจุดป้ายชื่อทุก ~2.6 กม. ได้ผู้สมัคร 6,412 จุด ยุบเหลือ **1,349 ป้ายชื่อ จาก 246 ชื่อไม่ซ้ำ** (`bg.json` โตจาก 135 เป็น 229 KB)

ตอนวาดจะกรองเฉพาะที่อยู่ในกรอบ เรียงลำดับความสำคัญ (แม่น้ำ > ทางด่วน > ถนนสายหลัก) กันไม่ให้ตัวอักษรทับกัน **หนึ่งชื่อต่อหนึ่งวิว** และจำกัดไม่เกิน 9 ป้ายต่อแผนที่ หมุนตัวอักษรตามแนวถนน

ก่อนใส่กติกา "หนึ่งชื่อต่อวิว" ป้ายชื่อถูกทางด่วนกินหมด เพราะทางพิเศษเส้นเดียวโผล่ซ้ำ 5-6 ครั้ง หลังใส่แล้วได้ ถ.เพชรบุรี ถ.พระราม 1 ถ.เพลินจิต ถนนรัชดาภิเษก ปนกันอย่างที่ควรเป็น

### ตัวเลขที่วัดจากต้นแบบจริง (เดสก์ท็อป)

| | ค่ากลาง | สูงสุด |
| --- | ---: | ---: |
| เปิดแผนที่ 1 สาย รวมการ paint | **3.5 ms** | 5.4 ms |
| สร้าง SVG ครบทั้ง 26 สายรวดเดียว | 11.8 ms | 35.6 ms |

- ฉากหลังทั้งชุด 2,570 เส้น + 1,349 ป้ายชื่อ = **192 KB ในหน่วยความจำ**
- ข้อมูลสายและเส้นทาง = 136 KB
- markup ของแผนที่หนึ่งใบ = 17.5 KB

**สรุป: แผนที่ออฟไลน์แทบไม่มีต้นทุน** ต่อให้มือถือกลางๆ ช้ากว่าเดสก์ท็อป 5 เท่าก็ยังราว 18 ms ต่อการเปิดหนึ่งครั้ง ซึ่งเป็นการกดครั้งเดียว ไม่ใช่การวาดซ้ำทุกเฟรม

### คำถามเรื่องสลับโหมด online/offline

ยังไม่ได้ทำ รอการตัดสินใจ — ต้นทุนที่แท้จริงไม่ใช่ความเร็ว แต่เป็นสองอย่างนี้: ขนาด bundle ที่เพิ่มจากไลบรารีแผนที่ (~42 KB gzipped) ซึ่งเล็กกว่าฉากหลังออฟไลน์ที่ยังไงก็ต้องมีอยู่ดี และ **ข้อมูลเน็ตราว 150-300 KB ต่อการเปิดแผนที่หนึ่งครั้ง** เทียบกับ 0 ของออฟไลน์ บวกเงื่อนไข ToS เรื่องการแคช tile ที่ต้องดูใน [WF-012](WF-012-osm-odbl-licence.md) และภาระการดูแลโค้ดสองทางสำหรับคนทำคนเดียว

## รอบที่ 6 — สถานที่ใกล้เคียง (คำตอบของเหตุผลที่อยากได้โหมดออนไลน์)

เหตุผลที่อยากได้โหมดออนไลน์คือ **อยากเห็นสถานที่ใกล้เคียง** ซึ่งเป็นความต้องการคนละอย่างกับ "อยากได้ tile" จึงตอบด้วยการอบสถานที่ลงในชั้นออฟไลน์ด้วยท่อเดิมแทน

ดึงจาก OSM: สถานีรถไฟฟ้า/รถไฟ ห้าง โรงพยาบาล มหาวิทยาลัย ตลาด ท่าเรือ ได้ 1,400 จุด มีชื่อ 1,234 จุด ยุบซ้ำในรัศมี 550 ม. เหลือ **1,194 จุด**

| ประเภท | จำนวน |
| --- | ---: |
| สถานีรถไฟฟ้า/รถไฟ | 238 |
| ห้าง | 286 |
| โรงพยาบาล | 185 |
| มหาวิทยาลัย | 81 |
| ตลาด | 267 |
| ท่าเรือ | 137 |

วาดไม่เกิน 7 จุดต่อแผนที่ และให้สิทธิ์ก่อนชื่อถนน (ซึ่งลดเหลือ 6) เพราะสถานีรถไฟฟ้าเป็นหมุดที่คนกรุงเทพใช้บอกตำแหน่งกันจริง

ผลคือแผนที่อ่านออกทันที เช่นสาย `2-44 (54)` เห็นเป็น *อนุสาวรีย์ → พญาไท → สยาม → ราชดำริ → อโศก → พระราม 9* ซึ่งเป็นภาษาที่ใช้บอกทางกันจริง

### performance หลังใส่ครบทุกชั้น

| | ค่ากลาง | สูงสุด |
| --- | ---: | ---: |
| เปิดแผนที่ 1 สาย รวม paint | **3.5 ms** | 8.9 ms |
| สร้าง SVG ครบ 26 สาย | 15.4 ms | 29.3 ms |

ฉากหลังครบชุด (2,570 เส้น + 1,349 ชื่อถนน + 1,194 สถานที่) = **240 KB ในหน่วยความจำ** · markup ต่อแผนที่ 18.8 KB · `bg.json` = 306 KB

**เพิ่มสถานที่เข้าไปแล้วเวลาเปิดไม่ขยับเลย** (3.5 ms เท่าเดิม) เพราะคอขวดอยู่ที่การกรองตามกรอบ ไม่ใช่จำนวนข้อมูลทั้งชุด

### ข้อสรุปเรื่องโหมดออนไลน์

ถ้าสิ่งที่ต้องการคือสถานที่ใกล้เคียง **ออฟไลน์ให้ได้แล้วโดยไม่ต้องมีโหมดที่สอง** — เหลือแค่คำถามว่าชุดสถานที่ 6 ประเภทนี้ครอบคลุมพอไหม ซึ่งถ้าไม่พอ ทางแก้คือเพิ่มประเภท (วัด โรงเรียน สวนสาธารณะ สถานที่ราชการ) ซึ่งถูกกว่าการดูแลโค้ดสองทางมาก

## Resolution

**หน้าจอหลักคือ variant D — รายการสายที่ขึ้นได้ โดยมีช่องกดเลขสายปักอยู่ด้านบน และกดแถวไหนก็ได้เพื่อเปิดแผนที่เส้นทางแบบออฟไลน์**

### หน้าจอหลัก

- **ช่องกดเลขสาย sticky อยู่บนสุด** ใช้ `inputmode="numeric"` เรียกแป้นตัวเลขของเครื่อง **ไม่ทำแป้นกดเอง**
- **ว่างไว้** → รายการสายที่ไปถึงจุดหมาย เรียงตามจำนวนป้ายที่เหลือ เลขสายตัวใหญ่ พร้อมข้อความหน้ารถและป้ายที่ต้องลง ส่วนสายที่ไม่ไปพับเก็บไว้กดดูได้
- **พิมพ์** → การ์ดตัดสิน **ขึ้นได้ / อย่าขึ้น / ไม่รู้จักสายนี้** ใต้ช่องกรอก และรายการข้างล่างกรองตาม
- **จับคู่เลขโดยตัดอักขระที่ไม่ใช่ตัวเลขและตัวอักษรทิ้ง** พิมพ์ `244` เจอ `2-44` พิมพ์ `54` ก็เจอ — ผู้ใช้ไม่ต้องหาปุ่มขีดบนแป้นตัวเลข ซึ่งแป้นมือถือส่วนใหญ่ไม่มี
- ทุกที่ที่บอกทิศ ใช้ **ข้อความหน้ารถ** เป็นตัวนำตามที่ WF-003 สรุป และมีบรรทัดบอกว่าแอปรู้จักแค่ ขสมก./TSB ตามที่ WF-006 เคาะ

### แผนที่เส้นทาง

กดแถวไหนก็ได้ → แผ่นซ้อนที่มีแผนที่ต่อด้วยลำดับป้ายแนวตั้ง เส้นเขียวถ้าไปถึง แดงถ้าไม่ถึง วาดเฉพาะช่วงที่วิ่งต่อจากป้ายที่ยืน

**ใช้แผนที่ออฟไลน์อย่างเดียว ไม่ทำโหมดออนไลน์** — เหตุผลที่อยากได้โหมดออนไลน์คืออยากเห็นสถานที่ใกล้เคียง ซึ่งแก้ได้ด้วยการอบสถานที่ลงในชั้นออฟไลน์ โดยไม่ต้องมีโค้ดชุดที่สอง ไม่ต้องใช้เน็ตตอนยืนที่ป้าย และไม่ต้องรับเงื่อนไข ToS เรื่องการแคช tile

ชั้นข้อมูลที่อบไว้ (จาก OpenStreetMap ผ่าน Overpass ตอน build ไม่ใช่ตอนใช้งาน):

| ชั้น | ปริมาณ |
| --- | ---: |
| แม่น้ำ/คลอง + ถนนสายหลัก | 2,570 เส้น |
| ชื่อถนน (หนึ่งชื่อต่อวิว สูงสุด 6) | 1,349 จุด |
| สถานที่ใกล้เคียง (สูงสุด 7 ต่อวิว) | 1,194 จุด |

รวม **240 KB ในหน่วยความจำ** และ **เปิดแผนที่ใช้เวลา 3.5 ms** (สูงสุด 8.9 ms) บนเดสก์ท็อป — การเพิ่มสถานที่ไม่ทำให้ช้าลงเลยเพราะคอขวดอยู่ที่การกรองตามกรอบวิว ไม่ใช่ขนาดข้อมูลทั้งชุด

### ข้อจำกัดที่ของจริงต้องรับมือ (เจอจากต้นแบบ ไม่ได้มาจากสเปค)

1. **ต้องกรองรถที่สุดสายที่ป้ายนี้ออก** — 9 จาก 37 รายการที่ป้ายทดสอบ การแสดง "รถที่จอดป้ายนี้" ไม่เท่ากับ "รถที่ขึ้นได้จากป้ายนี้"
2. **ต้องยุบระเบียนซ้ำในฟีด** ด้วยคู่ (เลขสาย, ข้อความหน้ารถ, จำนวนป้าย)
3. **ห้ามสร้าง DOM ใหม่ทั้งหน้าเวลาผู้ใช้พิมพ์** อัปเดตเฉพาะส่วนที่เปลี่ยน ไม่งั้นลบตัวเลขไม่ได้และ IME ภาษาไทยเพี้ยน
4. **ชื่อถนนต้องจำกัดหนึ่งชื่อต่อวิว** ไม่งั้นทางด่วนเส้นเดียวกินป้ายชื่อหมดทั้งแผนที่
5. **Overpass ตัวหลักใช้ไม่ได้** ต้องมีมิเรอร์สำรอง แต่เป็นงานตอน build จึงไม่กระทบผู้ใช้
