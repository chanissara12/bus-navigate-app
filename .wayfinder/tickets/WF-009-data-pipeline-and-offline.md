## Question

ฟีด Namtang เป็นซิป 41.8 MB ทั้งประเทศ ส่วน PWA ต้องเปิดได้เร็วตอนยืนที่ป้ายที่เน็ตห่วย ต้องพิสูจน์ด้วยของจริงว่าช่องว่างนี้ปิดได้

สร้างตัวแปลงแบบใช้แล้วทิ้ง แล้ววัดจริง:

1. กรองตามขอบเขตที่เคาะไว้ใน WF-006 แล้วเหลือข้อมูลกี่ MB
2. ลองรูปแบบเก็บที่ต่างกัน เช่น JSON, JSON ที่บีบอัด, SQLite ผ่าน wasm, IndexedDB แล้ววัดขนาดจริงกับเวลาค้นจริง
3. โหลดทั้งก้อนตอนติดตั้งครั้งแรก หรือโหลดเฉพาะส่วนที่ใช้ ข้อไหนทำให้ "เปิดแล้วใช้ได้ทันที" เป็นจริง
4. อัปเดตฟีดใหม่แล้วทำยังไง ซึ่งขึ้นกับ WF-004 โหลดใหม่ทั้งก้อนหรือทำ diff
5. เวลาค้น "สาย 8 ผ่านที่ไหนบ้าง" และ "จากป้ายนี้ไปที่นั่นขึ้นสายไหน" บนมือถือจริง ใช้เวลากี่ ms

ผลลัพธ์คือตัวเลขจริงที่ทำให้ตัดสินใจเรื่องสถาปัตยกรรมข้อมูลได้โดยไม่ต้องเดา

## เพิ่มเติมหลังปิด WF-011 — ความเสี่ยงลดลงมาก

[WF-011](WF-011-id-stability-across-versions.md) วัดไว้แล้วว่า **ข้อมูลที่แอปต้องแคชจริงมีแค่ราว 10.5 MB** (โตขึ้นแค่ 2.6 MB ใน 4 ปี) ส่วนที่ทำให้ซิปใหญ่คือ `shapes.txt` ซึ่งกิน 81% ของไบต์ที่เพิ่มขึ้น และเป็นเส้นวาดแผนที่ที่ MVP ยังไม่ต้องใช้ทั้งหมด (แต่ WF-003 ต้องใช้มันคำนวณฝั่งถนน — คำนวณล่วงหน้าตอน build แล้วเก็บแค่ผลลัพธ์ได้)

ticket นี้จึงเหลือคำถามว่า **เก็บด้วยอะไรและค้นเร็วแค่ไหน** มากกว่าคำถามว่าจะยัด 42 MB ลงมือถือยังไง

## Resolution

**ทั้งแอปเป็นไฟล์เดียว 377 KB (gzip) โหลดครั้งเดียวตอนติดตั้ง แล้ว parse 7 ms ทุกครั้งที่เปิด — ความซับซ้อนที่ตั๋วนี้กลัวไว้ไม่จำเป็นเลย**

### 1. รูปแบบเก็บ: packed array ไม่ใช่ JSON แบบ object

| | ดิบ | gzip | parse |
| --- | ---: | ---: | ---: |
| naive JSON (object ต่อแถว) | 2,663 KB | 599 KB | 21 ms |
| **packed** | **1,167 KB** | **312 KB** | **4 ms** |

การ pack คือเก็บเป็น array ขนาน ใช้ index ของป้ายแทน `stop_id` พิกัดเก็บเป็น delta ของจำนวนเต็ม (คูณ 1e5) และเวลาเก็บเป็นหน่วย 5 วินาที — **ลดขนาดได้มากกว่าครึ่งและ parse เร็วขึ้น 5 เท่า**

### 2. ขนาดแยกส่วน

| ส่วน | ดิบ | gzip |
| --- | ---: | ---: |
| ป้าย 6,703 จุด (ชื่อ + พิกัด) | 845 KB | 188 KB |
| สาย 536 ทิศ + ลำดับป้าย + เวลารายป้าย + headway | 409 KB | 75 KB |
| เส้นทางวาดแผนที่ 140 จุด/สาย | 1,405 KB | 288 KB |
| ฉากหลัง OSM (ถนน ชื่อถนน สถานที่) | 306 KB | 65 KB |
| **รวม packed + ฉากหลัง** | **1,473 KB** | **377 KB** |

**เส้นทางกินที่มากกว่าทุกอย่างรวมกัน** — ดิบมี 514,369 จุด (เฉลี่ย 961 จุด/สาย) = 10.4 MB ลดเหลือ **140 จุด/สาย** ได้ 1.4 MB โดยต้นแบบยังวาดสวย (40 จุดได้ 109 KB gzip แต่เส้นเป็นเหลี่ยม, 80 จุดได้ 196 KB ซึ่งยังดูดี ถ้าวันหนึ่งต้องรัดเข็มขัด)

### 3. โหลดทั้งก้อนตอนติดตั้ง ไม่ต้องโหลดทีละส่วน

377 KB เล็กกว่ารูปเดียวบนเว็บทั่วไป การแบ่งโหลดจึงเป็นความซับซ้อนที่ไม่ได้อะไรกลับมา — เก็บใน Cache Storage ผ่าน service worker แล้ว parse เข้าหน่วยความจำตอนเปิด

**ไม่ต้องใช้ IndexedDB และไม่ต้องใช้ SQLite wasm** สำหรับข้อมูลเส้นทาง ส่วนข้อมูลของผู้ใช้เอง (จุดหมายที่บันทึกไว้ สถานะระหว่างเดินทางของ [WF-014](WF-014-recover-from-misboarding.md)) มีขนาดไม่กี่ KB เก็บแยกได้ตามสะดวก

### 4. ความเร็วที่วัดได้ (เดสก์ท็อป)

| | ค่ากลาง | p95 |
| --- | ---: | ---: |
| **เปิดแอป: parse + สร้าง index ทั้งหมด** | **7.1 ms** | 17.6 ms |
| ค้นจากสาย (เลข → ลำดับป้ายทั้งสาย) | 0.002 ms | 0.004 ms |
| ป้ายรอบตัว รัศมี 400 ม. | 0.009 ms | 0.036 ms |
| **ค้นจากปลายทาง: สายตรง + ต่อ 1 ต่อ + จัดอันดับด้วยเวลา** | **1.7 ms** | 3.0 ms |

index ที่สร้างตอนเปิดคือ กริดเชิงพื้นที่ช่องละ ~1.1 กม. (1,128 ช่อง) และตารางเลขสายที่รองรับทั้งเลขเก่าและใหม่ (409 คีย์)

**และมันยืนยันว่ากติกาเรียงตามเวลาของ [WF-013](WF-013-transfer-ui.md) ใช้ได้จริง** — ผลของ อนุสาวรีย์ → วงเวียนใหญ่ ออกมาเป็นสายตรง 40 และ 41 นาทีนำหน้า แล้วตามด้วยการต่อรถที่ 44 นาที ส่วนทางเลือก 52 ป้ายที่เคยลอยขึ้นอันดับ 9 ด้วยกติกาเก่า หลุดออกจาก 5 อันดับแรกไปแล้ว

### 5. การอัปเดต: GitHub Actions รายสัปดาห์ที่เปิด PR

**แอปไม่เคยโหลดฟีด 42 MB เอง** — ขั้นตอน build เป็นคนโหลด แปลง แล้วได้ไฟล์ 377 KB ไป deploy

ให้ Actions รันรายสัปดาห์ โหลดฟีด แปลง แล้ว**เปิด PR ถ้าผลลัพธ์ต่างจากเดิม** ไม่ deploy อัตโนมัติ เพราะ [WF-004](WF-004-feed-licence-and-updates.md) พบว่าฟีดทับไฟล์ทุกคืนโดยไม่มี changelog และ [WF-011](WF-011-id-stability-across-versions.md) พบว่ามี `stop_id` ที่ความหมายเปลี่ยนโดยที่ id ไม่เปลี่ยน — **diff ใน PR คือจุดเดียวที่จะจับความเปลี่ยนแปลงแบบนั้นได้ก่อนที่จุดหมายที่ผู้ใช้บันทึกไว้จะเพี้ยนเงียบๆ**

ตอน import ทุกครั้งให้ตรวจ checksum (พิกัด, ชื่อ) ของป้ายที่ผู้ใช้บันทึกไว้ ตามที่ WF-011 กำหนด และเก็บสำเนาฟีดไว้เองตามที่ WF-004 กำหนด
