# [wayfinder:grilling] Wrong-bus recovery algorithm & Recovery Point search

**Parent map:** [Phase 1 Spec — Public Transit Decision & Recovery Assistant](../map.md)

**Status:** closed
**Blocked by:** none (all three prerequisites closed: ~~T03~~, ~~T04~~, ~~T05~~)
**Blocks:** [Full Phase 1 API contract](T09-api-contracts.md)

## Question

PROPOSAL.md sections 8-9 require, when a user reports "I took the wrong bus" (or is
inferred to have via `CurrentRoute` diverging from the planned route), generating
`RecoveryOption`s anchored on `RecoveryPoint`s (next stop, previous stop, transfer
point, nearby BTS/MRT, another reachable stop) — never forcing a return to the origin
of the problem.

Define:

- The search strategy for candidate Recovery Points given `CurrentLocation`/
  `CurrentRoute` — what's actually queried (nearby `BusStop`s within what radius,
  reachable `Direction`s from those stops, transfer stations if in the Phase 1 data
  model at all).
- How this reuses vs. duplicates the comparison logic from
  ["Can I take this bus?" comparison algorithm](T05-can-i-take-this-bus.md) — a
  RecoveryOption is structurally a TravelOption from a new CurrentLocation; confirm
  whether it's the literal same code path or a variant.
- How "get off at next stop" vs. "continue on current bus" are represented as options
  (section 8's option list) when the current bus hasn't necessarily diverged yet.
- Whether BTS/MRT stations are modeled as a distinct entity or as a special case of
  `Place`/`BusStop` for Phase 1 purposes (transfer connectivity data availability
  depends on what T01's data source actually includes for BTS/MRT — flag if this needs
  to fall back to a simpler "walk to a known transit hub" treatment for Phase 1).

## Resolution

**BTS/MRT stations:** modeled as plain `Place` entities (name + coordinates, sourced
from OSM `railway=station` tags — same approach as T02/T08's landmark data), carrying
**no route/schedule data** — Namtang GTFS (T01) covers only BMTA/affiliated bus routes,
not rail. A `RecoveryOption` pointing at a station is shown as an **unconfirmed
pointer**, not a computed itinerary: e.g. "BTS Asok is 300m away, may offer further
travel options" tagged `DataConfidence: Unknown`, clearly distinct from bus-based
`RecoveryOption`s that are fully computed and confirmed. See map's "Not yet specified"
for why full BTS/MRT routing is deliberately deferred rather than added now.

**Reuses T05's algorithm exactly, no relaxed thresholds:** a `RecoveryOption` is
generated by running the same accept/reject rule from
[T05](T05-can-i-take-this-bus.md) (unreachable → reject, >1 extra transfer → reject,
>800m extra walk → reject), just starting from the new `CurrentLocation` instead of
the original boarding stop. If nothing passes, the system says so explicitly
("no recommendable option within normal criteria") and separately surfaces the
least-bad candidate(s) under an explicit "last resort" category — never silently
loosening the thresholds, which would make a worse option look normal.

**"Continue on current bus"** is not special-cased — the current bus's `Direction`
from the user's current position is simply one more candidate run through the same
T05 check. If its remaining path still validly reaches the destination, it surfaces
as a `RecoveryOption` like any other (often the best one, since no alighting is
needed).

**Recovery Point search radius:** 800m — same as T05's walk budget, not a separate
constant, to keep the system's walking-distance tolerance consistent everywhere.

Feeds [T09](T09-api-contracts.md): the recovery-report endpoint and `RecoveryOption[]`
response shape (including the confirmed-vs-unconfirmed distinction for rail pointers).
