## Question

เรื่องนี้เคยอยู่ในหมอกเพราะ "ต้องใช้การคำนวณต่อรถซึ่งอยู่นอก MVP" แต่ [WF-008](WF-008-destination-lookup-engine.md) ตัดสินให้มีตัวคำนวณการต่อรถแล้ว และมันเร็ว 0.2 ms ข้อจำกัดเดิมจึงหายไป

นี่คือ **เคส A ในโจทย์ตั้งต้น** — เคสจริงที่เป็นต้นเรื่องของทั้งโปรเจกต์ ตอนนี้แอปตอบได้แค่ครึ่งเดียวคือ "คันนี้กำลังพาคุณไปไหน" แต่ยังไม่ตอบ "แล้วจะทำยังไงต่อ"

1. **แอปรู้ได้ยังไงว่าผู้ใช้ขึ้นผิด** — ให้กดบอกเอง (พิมพ์เลขสายที่นั่งอยู่ ซึ่งหน้าจอปัจจุบันทำได้แล้ว) หรือเดาจาก GPS ว่ากำลังเคลื่อนที่ไปตามเส้นทางของสายไหน
2. **เสนออะไร** — ลงป้ายไหนแล้วต่อสายอะไร / ลงเดี๋ยวนี้แล้วข้ามฝั่งขึ้นสายเดิมกลับ / บอกว่ายังไปถึงได้อยู่ไม่ต้องตกใจ ซึ่งบางครั้งเป็นคำตอบที่ถูก
3. **คิดจากตรงไหน** — จากป้ายถัดไปที่รถจะจอด ไม่ใช่จากป้ายที่ขึ้นมา ซึ่งแปลว่าต้องรู้ว่าตอนนี้อยู่ช่วงไหนของเส้นทางแล้ว
4. **ความแม่นของ GPS** — [WF-003](WF-003-stop-coords-side-of-road.md) วัดว่าป้ายสองฝั่งห่างกันราว 30 ม. ซึ่งชนกับความคลาดเคลื่อน GPS ในเมือง แต่การหาว่า "อยู่ช่วงไหนของสาย" ต้องการความแม่นระดับร้อยเมตร ไม่ใช่สิบเมตร จึงอาจพอ — ต้องตรวจก่อน
5. **ขอบเขต** — นี่เป็นฟีเจอร์ที่ทำงานระหว่างเดินทาง ต่างจากทุกอย่างที่ตัดสินใจมาซึ่งทำงานตอนยืนนิ่งอยู่ที่ป้าย ต้องเคาะว่าอยู่ใน MVP หรือเป็นรอบถัดไป

## Resolution

**อยู่ใน MVP · ผู้ใช้พิมพ์เลขสายเอง · GPS หาตำแหน่งบนสายนั้น · ตอบเป็นคำตอบเดียวชัดๆ**

### 1. รู้ว่าอยู่บนคันไหน: ผู้ใช้พิมพ์เอง

**GPS เดาไม่ได้** — ถ้าสุ่มจากการแวะป้ายจริงของทุกสาย ป้ายหนึ่งมีสายผ่านเฉลี่ย **9.6 สาย** (ค่ากลาง 3, p90 13, สูงสุด 40) การให้เลือกจากลิสต์ก็ช้ากว่าพิมพ์ **และผู้ใช้รู้เลขสายอยู่แล้วเพราะเพิ่งขึ้นรถคันนั้นมา** ช่องกดเลขบนหน้าจอหลักจาก [WF-010](WF-010-standing-at-the-stop-screen.md) รองรับอยู่แล้ว ไม่ต้องสร้างทางเข้าใหม่

### 2. รู้ว่าอยู่ตรงไหนของสาย: GPS จับคู่กับป้ายบนสายที่รู้แล้ว

พอรู้สายแล้ว ปัญหาเหลือแค่หาตำแหน่งบนเส้นเดียว ซึ่งวัดแล้วว่าทำได้: **ป้ายติดกันห่างค่ากลาง 348 เมตร** (p10 198 ม.) และมีแค่ **0.8% ที่ห่างกันน้อยกว่า 100 เมตร** เทียบกับความคลาดเคลื่อน GPS ในเมืองราว 20-50 เมตร

สังเกตว่านี่เป็นคนละปัญหากับที่ [WF-003](WF-003-stop-coords-side-of-road.md) เตือนไว้ — ตรงนั้นคือการแยกป้ายสองฝั่งถนนที่ห่างกัน 30 เมตร ซึ่ง GPS ทำไม่ได้ แต่การไล่ตำแหน่งบนเส้นเดียวที่ป้ายห่างกัน 348 เมตรเป็นคนละสเกล

**ทางสำรองเมื่อ GPS ใช้ไม่ได้**: ให้ผู้ใช้เลือกป้ายล่าสุดที่จำได้ · **ไม่ใช้การนับเวลาจากตอนขึ้น** เพราะรถติดทำให้เพี้ยนทันที

### 3. แสดงคำตอบเดียว ไม่ใช่รายการให้เทียบ

จาก 1,991 สถานการณ์จำลอง (นั่งอยู่บนสายที่ไม่ผ่านจุดหมาย) คำตอบเป็น **สองขั้ว ไม่มีตรงกลาง**

| | |
| --- | ---: |
| มีทางกู้ข้างหน้า | **75.5%** |
| ไม่มีเลยจนสุดสาย | 24.5% |
| ในเคสที่กู้ได้ — ลงป้ายถัดไปได้เลย | **46.2%** |
| แต่ p90 คือต้องนั่งต่ออีก | **22 ป้าย** |

จึงแสดงเป็นคำตอบเดียวสามแบบ: **"ลงป้ายหน้า"** / **"ยังลงไม่ได้ อีก N ป้าย"** / **"สายนี้ไม่มีทางกู้ ลงเมื่อไหร่ก็ได้แล้วค้นใหม่"**

เหตุผลที่ไม่ให้เปรียบเทียบเหมือนหน้าจอหลัก: ตอนนั่งอยู่บนรถที่ขึ้นผิด ผู้ใช้กำลังตกใจและมีเวลาไม่กี่วินาทีก่อนรถถึงป้ายหน้า เป็นคนละโหมดกับตอนยืนนิ่งที่ป้าย · และ **24.5% ที่กู้ไม่ได้ต้องพูดตรงๆ ว่ากู้ไม่ได้ ห้ามเสนอทางเลือกห่วยๆ มากลบ**

### 4. อยู่ใน MVP

เป็นเคสจริงข้อแรกที่เป็นต้นเรื่องของโปรเจกต์ ถ้าตัดออกก็เหลือแค่ครึ่งเดียวของปัญหาเดิม

**และของที่ต้องสร้างใหม่มีน้อยกว่าที่คิด** — "การกู้" คือการค้นจากปลายทางเดิมของ [WF-008](WF-008-destination-lookup-engine.md) แค่เปลี่ยนจุดตั้งต้นจาก "ป้ายที่ยืนอยู่" เป็น "ป้ายข้างหน้าบนสายที่นั่งอยู่" เครื่องคำนวณและหน้าจอใช้ของเดิมได้หมด

### สิ่งที่ตามมา

**โหมดการทำงานใหม่: ติดตามตำแหน่งระหว่างรถวิ่ง** — ทุกอย่างที่ตัดสินใจมาก่อนหน้านี้ทำงานตอนผู้ใช้ยืนนิ่งอยู่ที่ป้าย นี่เป็นครั้งแรกที่แอปต้องทำงานต่อเนื่องขณะเคลื่อนที่ กระทบ [WF-009](WF-009-data-pipeline-and-offline.md) เรื่องการเก็บสถานะระหว่างเดินทาง และเปิดหมอกของการเตือนตอนใกล้ถึงป้าย → [WF-016](WF-016-alight-alert.md)
